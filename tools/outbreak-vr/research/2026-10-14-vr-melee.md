# VR melee in File #1: a hit on contact, through the game's own hit code, with no attack action (2026-10-14)

Branch `vrmelee` (from `meleecoop`). Follows `2026-10-14-melee.md` (the canned swing, the attack object, caves A-C) and
`2026-10-14-melee-coop.md` (who owns enemies online). Static work on the slot-5 RAM dumps of File #1 (`ram5_a.bin`,
`ram5_b.bin`, from the melee session; nothing committed), then live offline runs of the `run-vrmelee` dev build,
headset-free, normal speed.

Evidence words: **verified** = read from the code or memory; **checked offline** = seen live in a headset-free run;
**assumed** = reasoned, not measured.

Why: after playing PhysicalMelee Alex said a swing sometimes "hangs for a second". The press path starts the game's
canned attack action (stance 2, sub-action 3), which locks the character for the whole motion (1.43 s for a pipe),
needs R1 first when the weapon is down (+0.6 s), and counts the stroke on the wind-up. This note is about not starting
that action at all: the VR weapon's own contact makes the game apply the hit.

## Short answer

- **The hit is not part of the attack action.** The swing's motion only *spawns* an attack object (`FUN_005521B0`) and
  later ends it; everything after that (the per-frame hit test, the damage, the reaction class, the hit sound and
  effect, the enemy's flinch, stagger, knockdown or death) is the attack object's node and the enemy's own damage state.
  So calling `FUN_005521B0` from a cave, with no action, gives a hit that is the game's own in every way but the
  character's motion (verified statically; checked offline below).
- **Enemy hurt volumes (verified):** every character has a list of spheres placed on its bones each frame: count u8
  `+0x1E0`, shapes `+0x1D8` (20 bytes each: f32 x 3 offset in the bone's frame, f32 radius `+0x0C`, u32 bone `+0x10`; a
  radius of -1 ends the list), world centres `+0x1DC` (12 bytes each). File #1's zombie (type 1): **head r 25 (bone 21),
  chest r 32 (bone 10), hips/legs r 30 (bone 3)**, shape list `0x6DFC80`. The hit zone the game records (`+0x13E`) is the
  sphere index.
- **Reaction classes (verified):** the hit stages a class 0, 1 or 2 in the enemy's `+0x140`, from a per-enemy-type table
  by attack id and distance band. For zombies: knives 0, pipes, brush and wooden pole 1, spear 2. The zombie's damage
  state (`FUN_00678750`) turns class 0 into a **light flinch** (a per-bone jolt, it keeps walking), class 1 into a flinch
  the first time and a **stagger** (state 3, sub 1) after that, class 2 into a **knockdown** (state 3, `FUN_00679510`), and
  HP at or below 0 into the fall.
- **Strength (verified):** the game's own "critical" (`FUN_00636990`, a chance per weapon type) returns a multiplier of 2;
  the damage is multiplied by it and **any multiplier above 1 promotes the class by one** (to at most 2). A cave on that
  function (cave E) multiplies its result by the host's strength for the VR strike only, so a hard swing staggers or
  knocks down where a soft one flinches, through the game's own rule.
- **Built (`PhysicalMeleeMode = Contact`, the new default):** the host tests the VR weapon's real hit shape (the game's
  own capsule or sphere for that weapon, on the VR weapon's pose) against every live enemy's spheres each input poll; on
  first contact faster than the weapon's threshold it asks cave D for a strike; cave D, run once a game frame just before
  the game's own hit test, calls `FUN_005521B0` for the local player and gives the new attack object a short life. Nothing
  is pressed, the character never enters an attack action, the hold (R1) stays whatever the player holds.

## 1. The hit-apply chain (verified)

From the attack object to the enemy's reaction, every step the game's own:

1. `FUN_005521B0(record, record + 0x50, record + 0x38, item index)` (the swing's spawn event calls it; 6 callers in all):
   needs the record's room `+0x1E2` = the current room (u16 `0x3065AC`) and the item's weapon object `item + 0x1C`;
   clears the record's `+0x115` bit 0; allocates an attack object (`FUN_00551E30`: updater `FUN_00552940` at `+0x14`,
   owner `+0x28`, life countdown s16 `+0x12`), and for blades, pipes and poles (weapon-type flags `0x10400`) makes it
   type 2 (`+0x04`), life -1 (until ended), position and matrix from the weapon object (caves A and B: from the VR block),
   then `FUN_005A9960(object, attack id, 0)` adds an attack node at the tail of the node list (head `0x23BDA0`, tail
   `0x23BD9C`), returning it in v0 (only on that path).
2. `FUN_00552940` (each frame): counts `+0x12` down and destroys the object at 0 (`FUN_00552BA0`); type 2 runs
   `FUN_00552CF0`, which copies the weapon's pose (cave A) until the owner's `+0x115` bit 0 is set, then marks the object
   ended (`+0x115` bit 0 of the object) and **clears the owner's bit** (it is a one-shot end request, set by the motion's
   end event).
3. `FUN_005A9DB0`, once a game frame from `0x5CDF64` (after the characters' updates, which fill the target list
   `0x3937A0`, count u16 `gp - 0x5E68`; it is zeroed at the end): per live node, its start delay and re-hit delay, then the
   shape tester by shape type (capsule `FUN_005AAE60`, sphere `FUN_005AA9B0`, ...). After a hit: the node's hit count
   `+0x28` against the parameters' limit `+0x0A` (0 for every File #1 melee weapon: **one hit per node**), else the re-hit
   delay `+0x0B`; `FUN_00548FC0` when `+0x1B` is set and `FUN_001B8C60(owner, params + 0x19)` (assumed: the hit effect and
   sound).
4. The capsule tester `FUN_005AAE60` builds the world segment (the shape's point P and P + D * length, through the
   object's matrix and position), tests walls (`FUN_005494C0`, only with params flag `0x10`), props (`FUN_0054D420`), then
   **`FUN_00549EA0(node, start, end, out)` with f12 = the capsule radius**: the enemy test.
5. `FUN_00549EA0` walks the target list: skips the owner, filters by the target's kind (`+0x02`; 0 player, 2 enemy) and
   the params' `+0x19` bits (no friendly fire for melee: `0x90`), then for each hurt sphere `FUN_00549BB0` (segment against
   a sphere: f12 the sphere's radius, f13 the capsule's). Melee params have `+0x0D` bit 0, so only the nearest sphere hit
   counts. On a hit, on the target: `+0x13F` hit counter +1; `FUN_0054B520(attacker, target)` picks the damage path; then
   **`FUN_00636990(attacker, node)`, the critical multiplier m**, and **`FUN_00578300(target, attacker, params, &class)`
   with f12 = m, the damage**, added to the staged s32 `+0x138` (clamped to s16). If the params' `+0x06` (priority) beats
   the target's `+0x13C`, the hit record is written: `+0x13C` priority, `+0x13D` params `+0x04`, `+0x140` **the class**,
   `+0x141` params `+0x12` (the hit kind: 1 melee, 3 bullet), `+0x142` the attack id, `+0x143` params `+0x17`, `+0x14C`/
   `+0x14D` params `+0x07`/`+0x08`, `+0x120` the hit point, **`+0x12C` the knock vector = (end - start) of the capsule,
   normalised (along the weapon's shaft, not the swing)**, `+0x13E` the sphere index.
6. `FUN_00578300` (the damage, verified): attack id = params `+0x13`; distance band by the attacker-target distance
   (under 200, under 600, else); the per-enemy-type table `0x707390[type]` gives, per (attack id, band), a percent and a
   class; the base damage is `0x700090[id]` (s16): **damage = base * percent / 100 * attacker `+0xBC4` (f32, 1.0) * m**
   (Mark's melee ids x1.5); then **if m > 1, class + 1 (to at most 2)**. Zombie (type 1), every band 100%:

   | Weapon (type) | Attack id | Base damage | Zombie class |
   |---|---|---|---|
   | Butcher knife (33) | 33 | 55 | 0 |
   | Kevin's knife (32) | 32 | 40 | 0 |
   | Iron pipe (34) | 34 | 60 | 1 |
   | Curved iron pipe (35) | 35 | 55 | 1 |
   | Scrub brush (41) | 41 | 40 | 1 |
   | Wooden pole (42) | 42 | 50 | 1 |
   | Spear (44) | 44 | 120 | 2 |

   These match the HP drops measured on `melee` (knife 55, pipe 60, brush 40, pole 50, spear 120; the extra 10 after a
   pipe swing is a second node, attack id 122, that the swing's own stage `FUN_006474A0` adds when its hit notice says an
   enemy was hit (section 7), not part of the hit; contact strikes do not add it).
7. `FUN_00636990(attacker, node)` (the critical, verified): the weapon type's f32 `+0x0C` (`0x6E594C` + 0x44 * id) is a
   percent chance; plus the attacker's `+0xBB0`; the attacker's `+0xBA4` bit `0x800` forces it; a hit is 2.0 (and a
   rumble for the local player), otherwise 1.0. 12 call sites in the testers.
8. The enemy's damage state (zombie: `FUN_00678750`, one of `FUN_0060F0C0`'s 20 callers): an effect by `+0x141` (table
   `0x6F74F0`), then `FUN_0060F0C0(enemy, attacker, 1000)` subtracts `+0x138` from HP `+0x544` (1: dead; 2: the enemy's
   accumulated damage `+0xC2E` reached the threshold; online only the room's master kills, see the co-op note), then by
   its own state and `+0x140`:
   - dead (or 2): `FUN_00679700`, the fall;
   - class 2, or class 1 with `+0xCEF` set: `FUN_006795C0`: state `+0x08` = 3 (hurt), then class 2 -> `FUN_00679510`
     (**knockdown**, `+0xBA3` = 1 or 2), class 1 -> sub `+0x09` = 1 (**stagger**), class 0 -> `FUN_00679490` (a flinch);
   - otherwise: `+0xCEF` = 1 and `FUN_005777B0(gp - 0x7148, enemy + 0xD1C)`: a **light flinch** that changes no state: up
     to a few entries of the enemy's per-bone jolt table `+0xD1C` (bone `+0x11`, active `+0x10`, time `+0x12`), from one of
     four random bone sets.

## 2. Contact mode (built)

### The patches (File #1 profile, `camera.silence`, `whenSetting: PhysicalMeleeContact`)

`PhysicalMeleeContact` is on with `[VR] PhysicalMelee` and `PhysicalMeleeMode = Contact`, under the same gate as
`PhysicalMelee` (strictly offline, or in private co-op only while this console runs the room's enemies with
`PhysicalMeleeOnline`). Caves A and B stay as they were (the attack object follows the VR weapon); cave C is harmless
(it only acts while the local player plays a canned swing).

- **Cave D** (`0xFE200`), reached from `0x5CDF64` (`jal FUN_005A9DB0` -> `jal 0xFE200`; the cave ends with
  `j FUN_005A9DB0`, so the game's hit test runs right after it, in the same frame). With the block's magic and its record
  it counts down the live strike; then, with a fresh stamp, when the host's strike number (`+0x0C`) differs from the one it served
  (`+0x10`) it takes it, and if the request is fresh (its own stamp `+0x28` at most 6 game frames old), no strike is
  live, and the record is not in the canned swing (stance 2, sub 3), it calls `FUN_005521B0(record, record + 0x50,
  record + 0x38, record's +0xC7C)`, and if a new node appeared at the list's tail owned by an object of this record, sets
  that object's life `+0x12` to the block's window (`+0x18`, frames) and notes it (`+0x14` the object, `+0x20` frames
  left, `+0x24` strikes made). The object then dies by itself after the window even if the caves come out meanwhile; the
  node dies at its first hit.
- **Cave E** (`0xFE400`), reached from `FUN_00636990`'s entry (`j 0xFE400`, its delay slot a nop): for the node of the
  live strike (node `+0x08` = block `+0x14`, with the magic) it runs the original function through a trampoline and
  multiplies its result by the block's strength (`+0x1C`, f32); for every other node it runs the original unchanged.

Block (`0xFF000`, host unless noted): `+0x00` magic, `+0x04` stamp, `+0x08` record, `+0x0C` strike number, `+0x10`
served (cave D), `+0x14` the live strike's object (cave D), `+0x18` window frames, `+0x1C` strength, `+0x20` frames left
(cave D), `+0x24` strikes made (cave D), `+0x28` the strike's stamp, `+0x40` matrix, `+0x80` position.

### The host (VR::PhysicalMelee, each input poll)

- The weapon's hit shape is read from the game: weapon type (`+0xCA8`) -> its attack id (`0x6E5940 + 0x44 * type +
  0x06`) -> params (`0x6E7C90 + 32 * id`, shape index `+0x0E`) -> `0x6EBFA0 + 8 * index` (type 3 capsule or 2 sphere,
  and its data). Placed on the VR weapon with the same matrix the block carries, it is exactly what the game will test.
- Against each live enemy (present, kind 2, HP above 0) and each of its spheres: segment (or sphere) to sphere, the
  radii summed, with a small lead (`contact.lead`, cm) so the strike is asked for a frame before the touch; the swept
  path between this poll and the last is tested too, so a fast swing cannot pass through between polls.
- Speed: the weapon's far hit point (the capsule's far end, the knife's sphere) in the headset's space, m/s, smoothed.
- Strike: on first contact with an armed enemy at or above `contact.speed` (per weapon), one strike (held up to
  `contact.holdMs`, 35 ms, while the tip still speeds up and still touches, so the strength is the swing's), then that enemy is
  disarmed until the weapon slows below `contact.rearm` or leaves it for `contact.leaveMs`; one strike live at a time.
- Strength: below `contact.firm` the multiplier rises from `contact.light` to 1 (less damage, the weapon's own class);
  from `firm` to `contact.heavy` it is 1 (the game's own hit); at or above `heavy` it is `contact.strong` (more damage and
  the class + 1: a pipe staggers on the first hit, a knife staggers instead of a jolt, a spear still knocks down).
- A buzz at the strike (`XRInput::QueuePulse`, by strength), and the enemy's HP drop is logged as before.
- **No hit-stop.** Alex hates hangs; the frame is never held. **No position write**: the push is the game's own reaction.

## 4. Ragdoll (research only)

What exists (verified): the hurt spheres' centres come from the enemy's **bone world matrices**, computed on the EE each
frame before the model is sent to VU1: `FUN_005AB840` reads them through `*(enemy + 0x34) + 0x820 + 4 * bone` (a
pointer per bone to a 4 x 4 row-vector matrix, row 3 the position). The zombie's light flinch is already a per-bone
procedural jolt (`FUN_005777B0`, table `+0xD1C`), applied on top of the animation.

What a ragdoll-lite would take, concretely:
1. Find the function that fills those bone matrices from the animation (the writer of `*(+0x34) + 0x820[k]`'s targets)
   and the point after it, before the draw list is built (the VU1 upload); a memwatch on one bone matrix of slot 5's
   zombie gives the writer PC. About half a day.
2. A cave there that, for an enemy with a live "hit impulse" in free RAM, rotates the hit bone (and its children, by the
   skeleton's parent table, also to find) about an axis perpendicular to the swing, decaying over ~0.3 s: a procedural
   bone offset, no physics. This is feasible because the matrices are plain EE memory; the hurt spheres would follow
   (they read the same matrices), which is fine. Two to three days with testing.
3. A real ragdoll (bodies falling with physics when knocked down or killed) would need joint limits, a solver, and
   collision with the room on the EE or the host per frame, and then writing every bone each frame against the game's
   own death and knockdown animations: weeks, and it fights the game's own state machine. Not recommended.
Online, any of it is cosmetic on this console only.

## 7. Durability and what partners see (branch `meleepolish`, 2026-10-15)

### Durability: where the game spends it (verified statically, checked offline)

- A melee hit tells its attacker: the hit (`FUN_00548E40`, for the node's object's owner) adds 1 to the record's
  **hit notice `+0x116`** and writes the target's kind and index in `+0x117`, `+0x118` (`+0x119`, `+0x11A` the target's
  owner, or 0xFF); a hit that only notifies (`FUN_00548FC0`, node `+0x1B`) writes its code with 0xFF in all four.
  `FUN_005ABA30` clears `+0x116` for every character each frame before the hit test (checked offline: the notice lives
  one frame), and the only reader that acts on it during an attack is the swing's own stage **`FUN_006474A0`** (stance 2,
  sub 3, phase 21, `0x647708`-`0x64775C`): code = `+0x116`, then if `+0x117`-`+0x11A` are all 0xFF code + 1, else 1;
  cleared.
- By the weapon type's class byte (`0x6E5945` + 0x44 * type): **class 4** (iron pipe, curved pipe, wooden pole): code 1
  (an enemy hit) spawns node 122 on the record (the extra 10 HP), clears `+0x115` bit 0, and for the local player
  (`+0x02` = 0, `+0x03` = the local slot `0x48BF7D`) sets **`+0xBA0` bit 31** and calls **`FUN_0062CDA0`** (the item-use
  mark: `+0xC7F` = `+0xC7C`, `+0xD92` |= 0x20, `+0xDA2` = slot); code 2 recoils (sub-phase 22, `+0x115` |= 1) and does
  the same; **class 5** (brush, spear): codes 1 and 2 the same mark (2 also recoils); **class 1** (knives): no mark (code
  2 recoils); bare hands a sound.
- The next character loop (`FUN_00638850`, `0x6388C4`) sees bit 31 and runs **`FUN_0062D2C0`**: clears it, then for the
  local player `FUN_0062CDE0(record, item)` -> **`FUN_00581A00(item, record)`**: with the item type's flag 1 (`0x716980`
  + 0x18 * `+0x2B`; the pipe's flags `0x02481001`) `FUN_00582040` subtracts by character for flag `0x2000000` (Kevin 4,
  David 2, Mark 6), keeps it at least 1, and below 2 with flag `0x80000` **breaks it** (`FUN_00584580`: count 0, then
  the item becomes the next kind with its own count: the iron pipe `0x67` bends into `0x68` with 20); otherwise
  `FUN_00581A00` takes 1 more. `FUN_0062CF10` (the shot) then returns at once for a weapon without the gun flag.
- So the earlier poked hits on `melee` did not spend because that poke left `+0xCA8` on the 45 (class 2), not because
  hits do not spend.

**Cave F** (`0xFE500`, 173 words, after cave D, which now ends `j 0xFE500`; the site at `0x5CDF64` checks caves D's and
F's first and last words): with the block's magic and record it runs the frame's hit test `FUN_005A9DB0` itself, then,
while a strike is watched (block `+0x38`, set to the window + 3 frames when cave D's strike count `+0x24` moves past cave
F's `+0x34`), handles a non-zero `+0x116` exactly as `FUN_006474A0` decides it (code, cleared, class 4 or 5 with code 1
or 2, local player): `+0xBA0` bit 31 and `FUN_0062CDA0`; `+0x3C` counts those uses. Never during the canned swing
(stance 2, sub 3: its own stage reads the notice) and never with bit 31 already set (next frame). Node 122 and the
recoil are left out on purpose (no extra hit, no action).

### What partners see (built, online only)

The type-1 state message is the only one that carries the action bytes, and the character loop sends it only when they
change (`0x639B24`-`0x639BC4`, filtered by `FUN_006337C0(record, previous stance, previous sub)`); `FUN_0064C620(record,

## 8. The zombie's own jolt, exactly (branch `hitjolt`, 2026-10-15; verified statically on `ram5_a.bin`)

- **Setter `FUN_005777B0(sets, table)`** (the zombie's damage state calls it 9 times with `sets` = `gp - 0x6F48` =
  `0x23AD28`, `table` = enemy `+0xD1C`): picks one of four 2-byte bone sets by `FUN_001ADEF0(1) & 3` (a random number) and
  fills **two** 20-byte entries: `+0x11` the bone, `+0x10` state 1, `+0x12` a delay of `2 / [0x23BF7C]` (that byte reads
  2, so 1 update); bone `0xFF` leaves the entry off. The zombie's sets: `{10, -}`, `{10, -}`, `{10, 12}`, `{10, 16}`: the
  waist (bone 10) always, a clavicle (12 or 16) half the time. (Section 1 said `gp - 0x7148`; it is `- 0x6F48`.)
- **Animator `FUN_00577870(enemy, params, table)`**, run every frame from the zombie's update (`0x6644D0`, right after
  `FUN_006031B0` and before `FUN_006798F0`), for each of the two entries by state: 1 counts the delay down, then 2; **2
  reads the hit record's knock vector `+0x12C` in the enemy's frame** (`FUN_00190E00` / `FUN_001913A0` with the enemy's
  matrix `+0x50`) and sets the two angles from the per-type params (`0x6E4C78` for the zombie, 3 s16 per entry: entry 0
  `3000, 1875, 6`, entry 1 `-4000, -1875, 6`): the minor horizontal component times the first, the dominant one times
  the second (so the larger angle always follows the knock's dominant axis), and the rates `-angle / 6 / 2`; 3 adds the
  rates each update until each angle crosses zero, then the entry goes off. Every live state calls the apply.
- **Apply `FUN_0055C450(enemy, bone, entry)`**: `FUN_00340210(x, y, z, *(*(enemy + 0x34) + 0x820 + 4 * bone) + 0x40)`:
  three u16 angles (65536 a turn, `FUN_00191950`) from entry `+0x00`, `+0x02`, `+0x04`, and `FUN_001903E0` rotates the
  **bone's local matrix** (`+0x40`, relative to its parent; row 3 the joint's offset, untouched) in place by X, then Y,
  then Z, about the parent's axes. The hierarchy is concatenated later in the frame, so children follow (a waist jolt
  moves the chest, arms and head). `+0x04` (z) is applied but never set or decayed by the animator.
- **So**: about 16 + 10 deg on the waist (and a clavicle), linear back to zero over 12 updates, its direction set only
  by `+0x12C`, which for a melee hit is the capsule's axis (the weapon's shaft, section 1), not the swing: the game's
  jolt cannot be given a direction for a VR strike without changing the hit record, and it never rolls (z).
- **The bone structs** (`*(enemy + 0x34) + 0x820` is a pointer per bone, 0x190 bytes apart): `+0x00` the world matrix
  (4 x 4 row vectors, row 3 the joint's position), `+0x40` the local matrix, `+0x80` the inverse bind matrix. The
  zombie has 36 bones; its parents (from `local x parent world = world`, error under 0.003): 1 <- 0, 2 <- 1 (pelvis,
  104 up), 3 <- 2 (the legs' root; 4-6 and 7-9 the legs), 10 <- 2 (waist, 105), 11 <- 10 (chest, 121), 12 / 16 <- 11
  (clavicles; arms 13-15, 17-19), 20 <- 11 (neck, 137), 21 <- 20 (head, 141), 22-27 <- 21 (face). The hurt spheres
  sit at the head (bone 21, 137 up), the belly (bone 10, 92 up) and the knees (bone 3, 32 up).
