# Resident Evil Outbreak File #1: an RE atlas for one-to-one VR (2026-10-22)

Alex, 2026-10-21: "I want this to really feel like a one-to-one experience... Resident Evil Outbreak VR, not something
thrown over the top." This note does three things:
1. It audits every VR feature in the build: the game's own, or ours on top.
2. It maps the game systems we have not touched yet, as far as this pass got.
3. It ranks the eight reverse-engineering conversions that would move the build the most.

How this was made: read-only and static. It uses the J's Bar RAM dump (`ui/ram_now.bin`) and the savestates already
extracted to the session scratchpad (`truevr/f1_0N`), never committed. No emulator, no builds and no game writes. It
builds on every note in this folder (`2026-10-21-true-stereo.md` is on branch `truestereo`, `-vr-presence.md` on
`vrpresence`, `-hand-pickup.md` on `handpickup`, `-grab-first-person.md` on `grabdoor`) and on the 2026-10-15 review.

Labels:
- **verified (code)**: read in the disassembly;
- **verified (memory)**: read in a dump;
- **assumed**: reasoned, not checked;
- **open**: not mapped yet.

**Coverage:** the five parallel static surveys (sound, animation, HUD and event scripts, AI senses, collision) are
folded into §2. Their scratch (`scratchpad/reatlas/<area>/`) holds disassembly and probe scripts but no written
findings, so each area was rebuilt by reading those files, re-running the probes against the J's Bar dump and
savestates, and following a few leads further. The thin spots are named in the area where they sit.

The surveys' scratch was read in full. Probe scripts that printed data (animation tables, collision grids, the
emitter and cache tables) were re-run against the J's Bar RAM dump and savestates 04 and 07; the states agree. None of

### (a) Sound: positioning mapped, listener found; voice back end and vibration open

**The old question is answered (verified (code)): the listener is the game camera.** Every positional sound goes
through one routine that reads the view matrix at `0x3062E0`. First person writes that camera from the head, so the
sound follows the head wherever the head pose reaches `0x3062E0` before the call (assumed: up to one tick late; the
matrix is rebuilt by `0x345740`).

| Address | What | Label |
|---|---|---|
| `0x1B7A70(group a0, id a1, owner a2, pos* a3, table t0, update t1, extra t2)` | The positional play call, 25 call sites. `pos*` points at an f32 xyz, normally a record's `+0x38`. A null `pos*` goes through `0x1B7A00` and `0x1B7A50`, which start the sound with every positioning argument -1 (the sound record's defaults). `0x1B7A00(pos*, id)` is group 1 with table 2. `a2` is passed on, but `0x1ABAA0` overwrites it unread. | verified (code) |
| inside `0x1B7A70` | `0x1B7B50` returns volume and pan, or 0, and 0 means nothing plays. Otherwise `t1 == 0` starts the voice with `0x1ABAA0(group, id, owner, vol, pan, -1, extra)`, and `t1 != 0` updates a playing voice with `0x1ABE10(..., 8192)`. Pitch 1.0 as 8192 is assumed. | verified (code) |
| `0x1B7B50(pos*, curve*, &vol, &pan)` | The camera is `0x190E00(tmp, 0x3062E0)`, a VU0 4x4 inverse, and row 3 of the result is the eye. The eye derived from `0x3062E0` equals the game's eye `0x306338` to 0.1 cm in the J's Bar dump. d = distance from `pos*` to the eye (`0x341860` is sqrt). d > 4800: returns 0. d <= 100: volume = curve[0], pan 63 (centre). In between: i = floor(d / 300) (`0x191BC0`), volume = linear blend of curve[i] and curve[i+1] over the 300-unit band; a volume of 0 returns 0. | verified (code); eye check verified (memory) |
| the pan | `0x191A10` carries `pos*` through the camera matrices (two scratchpad matrices at `0x70003700` and `0x70003F40`, then the block `0x2771E0`). x is clamped to 0..640, mirrored (640 - x) when w < 0, and pan = int(x / 5.0394); 5.0394 (`gp-0x7F74`) is 640/127. So the pan is the emitter's screen x under the game camera, 0..127, and a sound behind the camera mirrors. The VU math was not traced; the constants fit. `0x2771E0` holds 527.5, -615.4, -256, -224 in the dump (focal lengths and a centre, assumed; whether our FOV write reaches it is unchecked). Other callbacks: `0x1B8510` (a random one-shot every 60 ticks) and `0x1B86D0` (follows an object, position from `0x1B8000`). `0x1B80D0` starts the loops (called from the room-load handler `0x5CE080` and the status-4 handler `0x5CE2F0`). | verified (code); slots verified (memory); that group 2 is ambience assumed |

### (b) Animation: channels, motion tables, evaluation and an aim solver mapped; the sampler and the arms' source open

**Channels (verified (code); flag names assumed).**
- A character record holds two banks of 12 channels, 0x20 bytes each: bank 0 at `+0x1E4` (the skeleton object behind
  `model+0`), bank 1 at `+0x364` (behind `model+4`); `0x55CE10` takes the bank from a flag argument. Which characters
  use bank 1 was not checked.
- Channel fields: `+0x00` f32 time in frames, `+0x04` f32 clip length, `+0x08` f32 loop restart, `+0x0C` s8 loops,
  `+0x0D` flags (0x08 blending, 0x10 holding, 0x20 looped this tick, 0x40 ended), `+0x0E` u16 motion id, `+0x10` f32
  blend step (1 / (1 + blend frames)), `+0x14` f32 blend position, `+0x18` u16 blend frames left.
- Channel 0's time, length and motion id (`+0x1E4`, `+0x1E8`, `+0x1F2`) are the ones the earlier notes use. Channel
  1's motion id is `+0x212`.

**Motion tables (verified (memory)).**
- `rec+0x518` points at the character's table: `0x4B9AF0` for ids 0 and 1 (Kevin, Mark) and `0x4B7BA0` for the id-7
  record (Cindy) in the dump.
- Layout: `+1` u8 5 (clips per motion), `+2` u8 mode 1, `+4` u16[2000] clip ids, `+0xFA4` u16[2000] first index per
  motion id.
- Clip for motion m on channel c = `u16[+4 + 2*(u16[+0xFA4 + 2*m] + c)]`. Clip 0 means none.
- The table `0x4B9AF0` (records 0 and 1) has 218 motions (ids 100, 101, 102, 103, 107, 123, ...). Motion 100 is base
  5: clips 37 and 38, then 0, 0, 0. Cindy's table uses clips 245 up.

**Calls (verified (code)).**
- `0x55B6D0(rec, table, motion id, channel, speed f12, blend f13)` (14 call sites) sets a channel's motion: the table
  lookup above, `0x1925C0(skeleton, clip, channel)` binds the clip, `0x192BD0(skeleton, channel, rate)` sets the rate,
  `0x192740`/`0x192760` read the clip length and loop. A zero clip on channel 2 clears it.
- `0x5A4490(rec, code, speed, blend)` is the action layer's "play this" call, 538 call sites (the action handlers
  `0x54ECB8` to `0x59A0D4` and more). `code` is a u16 such as 0x2001, 0x2003, 0x2021, 0x1011, 0x2050 and 0x2051. It
  stores `+0x520`, looks the row up with `0x5A3E60(rec, code)` (4 s16 per row) and plays it with `0x5A4890`. That
  starts channel 1 and channel 0 (`+0x212`, `+0x1F2`), clears channels 2 to 4 (`0x192500`), restarts them with the
  same motion id, and writes pose offsets (`+0xCB8`, `+0xCC8`..; not decoded).
- Per tick: `0x55BC80(channel, step)` returns 0 playing, 1 ended, 2 looped, 3 zero length. `0x55BE60(rec, channel,
  step)` wraps it and, for channel 0, moves the root-motion accumulator (`+0x4E4`, `+0x4F0`, `+0x4FC`, `+0x508` xyz;
  assumed consumed as movement). `0x55C190` blends. The byte `0x30659C` doubles every step when non-zero (assumed: a
  frame-rate compensation).
- Motion events: `0x543410` -> `0x5654D0` -> `0x565C80`, as before.

**Evaluation and the hierarchy (verified (code)).**

  (`+0x00`) = (local `+0x40` with scale `+0x104` and translation `+0x70`) x parent. Siblings are `+0xCC`, children
  `+0xD0`, parent `+0xC8`.

**Clip sampler (verified (code); meaning assumed).**
- `0x193620` reads a clip: u16 header (high nibble 1 or 2), s16 track count at `+2`, track list at the offset in `+4`
  (base `gp-0x625C`), 8 bytes per track (`+0` decoder type, `+1` parameter index). `0x18DE40` dispatches the decoder
  by type: 0x21, 0x22, 0x23, 0x11, 0x12, 0x13 go to `0x18DF00`, `0x18DF80`, `0x18E010`, `0x18E0E0`, `0x18E190`,
  `0x18E250`. Parameters 3, 4 and 5 are scaled by a gp constant and the rest divided by 16: assumed rotation and
  translation.

  function reaches it (the surveys' call-graph search found none; probably function pointers). So where the pose is
  sampled in the tick is not established.

**Aim solver `0x5E9600(rec, set)` (verified (code) and (memory)).**
- Data: sets `0x6DB6C0` (8 bytes, up to 4 entry ids, -1 ends; in this build sets 0 to 3 hold entry 0 to 3 alone),
  entries `0x6DB6E0` (18 bytes, 9 s16), bone ranges `0x6DB730` ((36, 38), (73, 75), (75, 77), (73, 75)), rows
  `0x6DB740` (12 bytes), f32 tables `0x6DB780`, `0x6DB790` (vec3) and `0x6DB7C0`, limits `0x6DB7D0` (6 f32 each,
  yaw and pitch ranges), blend weights at `0x23ABB0` (0.8, 0.9).
- What it does: per entry it builds a target from the tables (via bone 10), and per bone in the range works out the
  direction to it, clamps yaw and pitch to the limits, builds the rotation (`0x18FC10`, `0x18FAD0`) and writes it into
  the bone's local rows (`+0x40`, `+0x50`, `+0x60`). Then it calls `0x192BE0(skeleton, root)`, and `0x5E9CF0`
  re-links the bone parents (`+0xC8`, `+0xCC`, `+0xD0`) from a list per set (`0x6DB890`).
- Who picks the set: `0x5E9390(rec)` (call sites `0x638A20`, `0x6516FC`, `0x5BC0C4`, `0x5BC10C`) indexes byte tables
  by the character id `+0xB98`: `0x23ABA0` and `0x23ABA8` for humans, `0x6DB500`, `0x6DB5E0` and others by class.
  In the dump only id 7 (Cindy) has a set (0 and 1 in the two gp tables); ids 0 and 1 hold 255 (none) and the other
  tables are all 255.
- Kevin's model has 36 bones (u16 at model `+0x816`), and the sets address bones 36, 37 and 73 to 76, so as shipped
  they cannot act on him.
- `0x5E9220` is the pass-1 sibling (call sites `0x638574`, `0x6513A0`); it touches the same tables and was not read.

**Aim height (verified (code); `0x191A70` as abs assumed).**

  clips, was not found.

### (e) Enemy AI senses: mapped by code; nothing hostile was alive in the dumps to check it against

All three savestates are J's Bar. The enemy array holds only bar patrons, the cache tables and lists are empty, and
every claim below is **verified (code)** unless it says (memory) or assumed.

**The records (verified (memory) for the patrons).** Enemies: `0x3FFCA0 + 0xD90*n`, `+6` is the enemy's own index (43
to 49 in J's Bar; the cache covers 50). NPCs: 10 slots at `0x3E8230`, stride `0x1170`, kind `+2` = 1 (one present in
J's Bar, index 9); the list `gp-0x5E6C` walks the NPC records (assumed the same objects). Characters: 8 records at
`0x476DD0`, only 3 present.

**1. The perception cache `0x6A3B60`, once per tick.** For each present character `i` (8 records) and each present
enemy `j` of the 50 (same room `+0x1E2`, `+0xC94` bit 0x100 clear) it fills an 8-byte cell at `0x385490 + 400*i +
8*j`:
- `+0` f32 distance (`0x1916E0` between the two records' `+0x38` positions);
- `+4` u16 bearing (`0x346C50`, from the character's chest, bone 11, to the enemy's bone `+0x551`);
- `+6` u8 blocked: 1 if the distance is over 3000, else the result of the wall ray `0x549860` (any hit, mask `0x4FFFF`)
  between the same two points;
- `+7` u8 from a second ray test, `0x54D4F0(a, b, 255, 129)`; meaning not decoded.

For the 10 NPCs against the 50 enemies it fills `0x3844F0 + 400*n + 8*j` (distance and bearing, `+6` and `+7`
cleared). It also builds, per character, a u8 list of the enemy indexes in range (255 ends it) at `0x3840E0 + 50*i`,
and for NPCs at `0x383D50 + 50*n`, using the helper `0x6A4680` (assumed an insertion sort by distance). The 8x8
character-to-character distance and bearing matrix at `0x386110` is built only when `0x1AF4D0` returns 1; its meaning
was not decoded (it sits next to the other network tests `0x1AF510` and `0x60EF30`).

Readers of the cache:
- `0x5794A0` and `0x579870` return the distance for a character or an NPC target: the cell, or the live distance when
  the enemy's `+0xC94` bit 0x40 is set. `0x579660` and `0x5799C0` return the bearing, `0x5797A0` the blocked flag.
  `0x5794A0` masks the row with `& 3`, so enemies read only characters 0 to 3. `0x5797A0` returns 0 when the enemy's
  `+0xC94` bit 0x10 is set, and `0x579660` returns the stored bearing `+0xBD8` when bit 0x80 is set.
- The player's lock-on picker `0x62D3B0`/`0x62D700` walks the same lists, so the lock-on and the AI use one model of
  "who is near whom".

**2. The senses, once per enemy per tick.** The enemy's think step calls `0x604750(enemy, view angle, eye bone, sight,
near)` with `+0xC8C`, `+0xD55`, `+0xBCC`, `+0xBD0`; `0x664D00` and the update `0x68C2A0` do so. That runs `0x604870`,
which sweeps the 4 characters and then the 10 NPCs.

Enemy fields it uses:

| `+0xBCC` f32 | sight distance | 400, 1800, 1e8 |
| `+0xBD0` f32 | near radius (all-round) | 100, 700, 200 |
| `+0xC8C` u32 | view angle, 0x10000 = 360 deg | 0x8000, 0x9FF6 |
| `+0xD55` u8 | eye bone (21 = head) | 21 (`0x664600` writes 14 for some types) |
| `+0xBA4` u32 | target mode, low byte 0, 1 or 2 | 0 or 1 |
| `+0xBF8` u16[2][10] | threat per target, row 0 characters, row 1 NPCs, 8191 max | all 0 |
| `+0xBB6` u8[4] | candidate order | e.g. 2, 1, 3, 0 |
| `+0xC25`/`+0xC26` | chosen target kind and index | 0, 0 |
| `+0xBD4` f32, `+0xBD8` u16 | distance and bearing to it | 352.8 |
| `+0xC30`/`+0xC32` s16 | lock timers | 0 |
| `+0xC94` bits | 0x800 target acquired, 0x20 alert lock, 0x40 live distance, 0x100 excluded from the cache, 0x10 never blocked, 0x80 stored bearing | 0x301, 0x309 |
| `+0xC20` to `+0xC23`, `+0xC89`, `+0xC8A` | gain and decay classes; not named | |

A candidate counts only if it is present and in the same room, `0x634640` is false (it returns 1 for an absent record
or one whose status `+0xBA0` has any of the bits 0x5E0), its action `+0x54F` is not 10 and its `+0xBA0` bit 8 is clear. Then `0x604D40` runs:
- The distance d comes from the cache.
- **Noise:** if d <= 800 and the target's `+0xD10` (a noise class its actions set) selects a non-zero s16 in the table
  at `0x6DC770`, that value times a per-enemy byte (`0x71A08C + 0x60*(enemy +0xB98)`) is added to the threat (capped at 8191).
  The same 0x60-stride table holds the HP mirror (`0x71A04C + 0x60*slot`, see the hit reaction); that it is one struct
  per slot is assumed.
- **Sight** is skipped, leaving only hearing, if the cache says blocked (`0x5797A0`), if d > sight, if `0x636F60(target)` is true (id `+0xB98` = 2 in action 0x41; in the standard order id 2 is Jim and 0x41
  would be his play-dead action, assumed), or if the target's `+0xBA0` has bit 0x20000000.
- Otherwise `0x602F10` gives the angle between the enemy's heading `+0x92` and the bearing to the target. Inside +- half
  the view angle: `0x605140` with gain x1. Outside it but within the near radius: gain x2. Beyond the near radius:
  decay `0x6054B0`. Past the sight distance: decay.
- **Gain** `0x605140`: amount = 400 - 2d / divisor (table `0x6FB4A0` by `+0xC89`), minimum 1, times modifiers from
  `+0xC20` to `+0xC23` and the target's `+0xB99`, with a random term in some modes; added to the threat, clamped to 0
  to 8191. **Decay** `0x6054B0`: subtract 2500 / divisor (table `0x6FB4C0` by `+0xC8A`) + 1, whatever the distance.

**3. Picking the target `0x604000(enemy, 4000)`.** By `+0xBA4` (0, 1 or 2): 0 characters only (`0x604220`), 1 characters
then NPCs (`0x604520`) if no character was chosen, 2 NPCs first.
- `0x604220` takes at once any character within `R + 100` of the enemy, where R is the u16 at `0x6FB510[enemy +3]`
  (its threat jumps to 8191). Otherwise, with the lock timer `+0xC32` expired, it takes the first candidate in
  `+0xBB6` order whose threat exceeds the threshold 4000 and whose height difference is within 170.
- Result: kind and index in `+0xC25`/`+0xC26`, the record pointer in `+0x24`, bearing `+0xBD8`, distance `+0xBD4`,
  `+0xC94` bit 0x800.

**What the AI reads from a player:** the chest bone's world position (cache rays and bearing), the record position,
the action `+0x54F`, status `+0xBA0`, id `+0xB98`, noise class `+0xD10` and `+0xB99`. It does not read the player's
heading `+0x92`; the cone is the enemy's own. So our head and controller heading changes do not change being seen,
except through the actions they trigger (aiming, running) and the noise class.

**The hit reaction `0x68E760`** runs when the hit counter `+0x13F` is set and the state is not 0 or 4.
- The attacker comes from `0x605D80` (attack node kind `+0x14A`: 0 a character record by `+0x14B`, 1 an NPC, 2 an
  enemy, and more).
- If the attacker is a human and the enemy's current motion (`+0x1F2`) is 102, 103 or 112 (assumed the downed poses),
  the attacker's aim class (`0x636E20`, §2b) must be 1 or 3 or the hit is dropped. So a downed enemy takes a hit only
  when the aim is more than 15 deg off level. This replaces the old note's "types 102, 103 and 112": they are motion
  ids, not enemy types, and the routine is the hit reaction, not a sense.
- Otherwise `0x60F0C0(enemy, attacker, 1000)` applies the staged damage `+0x138` to the HP `+0x544` (0x7FFF is
  immortal) and returns 0 alive, 1 dead or 2 heavy. Dead sets state `+8` = 4; hurt sets 3 with a flinch counter at
  `+0x10` (8 divided by the byte at `gp-0x5CF4`), or, when heavy, state 1 with sub-action 6; `+0x140` picks the
  sub-action and `+0x141` a handler from the pointer table `0x6F74F0` (called with 19 as its argument). The HP is
  mirrored into a per-slot table at `0x71A04C + 0x60*(+0xB98)`.

**Enemy update structure:** `0x664290` runs the state function from the table `0x6E49E0[+8]`, `0x68C2A0` from
`0x6FB8F0[+8]`. A state function dispatches again on `+9` (tables `0x6E4AB0`, `0x6E4AF0`, `0x6E4B60`, `0x6E4C40`,
`0x6E4CF0`) and on the phase `+0xA` (`0x6E5690`). The init `0x664600` is by type `+4` (9, 6, and others).

**For VR:** the AI sees the game's chest bone, not the VR head. Nothing in VR changes it except the actions and the
aim class. A VR body that leans the torso would change bone 11 and so the rays and bearing.

**Open:** the lock picker body `0x62D3B0` (only its helper `0x62D700` was in the scratch), the table values and the
modifier bytes, `0x54D4F0`, `0x1AF4D0`, the enemies' attack code, and the live behaviour (the dumps have no zombie).

damage code uses: offline it returns 1, online it compares the room's master with the local slot. Which of the sense

### (f) Collision: world data, ray, floor and movement mapped

**World data (verified (code) and (memory)).** `0x5E4E00(blob)` loads a room's collision into two grid headers of 0x20
bytes: `0x3938A8` (A, walls) and `0x3938C8` (B, floors). Layout: `+0` s32 cell width, `+4` cell depth, `+8` u32 cells
in x, `+0xC` cells in z, `+0x10` s32 origin x, `+0x14` origin z, `+0x18` pointer to the cell array (u32 per cell, index
`ix*nz + iz`, each a pointer to a list of face pointers ended by 0xFFFFFFFF), `+0x1C` pointer to the faces. A runtime
attribute mask `u32 0x3938E8` (cleared at room load) is tested by the face filter.

J's Bar (dump): both grids have cells of 300 x 300, 6 x 6 cells, origin (7750, 12200). Grid A has 143 faces, all
vertical, y from -50 to 300, attribute words (flags >> 16) 0x29, 0x2F, 0x12F and 0x22F (137 faces of class 0, 6 of
class 1); 266 cell references.
Grid B has 21 faces, all floors, mostly at y = 0 and a few at y = 20 (a raised area at x 8100 to 8700, z 12450 to
12886).

**A face is 56 bytes (verified (code), numbers (memory)).** `+0` u32 flags (byte 0 class 0 to 15, byte 1 a second
class byte, bits 16 to 31 an attribute mask), `+4`, `+0x10`, `+0x1C` three f32 xyz vertices, `+0x28` normal xyz,
`+0x34` plane constant d. `0x5E61E0(flags)` returns (flags & 0xFFFF0000) | (1 << class), the word the callers test.

`0x5E6050(face, maskA, maskB, a3)` is the face filter. The masks have the layout of that word (class bits low,
attribute bits high). A face passes if its class bit is in maskA's low half and its attribute bits meet maskA's high
half, and maskB (same layout) does not exclude it, and the room-wide mask `u32 0x3938E8` does not. Class-1 faces then
go through a door check: the attribute bits 8 to 11 (flags bits 24 to 27) index a 0x60-stride table at `0x4747C0`,
and the face blocks while that entry's byte at `+1` is not 2 (an open door holds 2; a bit 0x40 in the attribute
word also lets it pass). A second byte at `+0x14` is read when `a3` is non-zero. In J's Bar the two class-1
attributes (0x12F, 0x22F) point at entries 1 and 2, whose bytes are 0, so those faces block: closed doors (assumed).

**The ray (verified (code)).**
- `0x5494C0(start*, end*, outHit*, outNormal*, maskA t0, maskB t1, outAttr* t2)` returns 1 on a hit. It is the answer
  to the old "arguments and grid layout" question. 53 call sites (weapons, enemies, character probes, ...).
- `0x549610` walks the segment in steps of 170 (the cell diagonal 424 / 2.5), collecting each new cell's list. The
  extra list at `0x70E6D0` is always appended. `0x549020` tests each list: filter `0x5E6050`, then `0x5491E0` (plane
  distance, hit point, point-in-triangle `0x5E58E0`), keeping the nearest. The end point shrinks to each hit so later
  cells can only find closer ones.
- Callers treat a hit as a solid wall when the attribute word has bit 0 (class 0) and bit 16 (attribute bit 0); they
  pass (-1, 0) for the masks.
- `0x549860(start*, end*, maskA, maskB, ...)` -> `0x549930` is the any-hit form (25 call sites; the perception
  cache uses it).
- What is at `0x70E6D0` (also read by `0x549860`, `0x54DB30` and `0x5E8180`) was not decoded; it looks like faces
  that move (assumed).

**The floor (verified (code)).** `0x5E5C20(pos*, outNormal*, ?, outClass*, classByte, outAttr*, outAttr16*, flag)`
queries grid B: the cell list through `0x5E5F10`, up-facing faces (normal y > 0) with the point inside the triangle
in x and z (`0x340C50`), the highest plane height within 100 above the query y. Wrappers: `0x5E5AF0`, `0x5E5B40`. The
height becomes `rec+0x170`, and a record's y is set to it unless its airborne byte `+0xBA5` is set (`0x606030`).

**Movement (verified (code)).** `0x5E63E0(newPos*, oldPos*, ..., radius f12, maskA, maskB, flag)` is a swept circle
against grid A: `2 * radius / cell + 2` sub-steps, giving a push vector and the hit. `0x5A9AC0(rec)` calls it with the
record's capsule (centre offset `+0x1AC`, radius `+0x1B8`, masks `+0x190` and `+0x194`) and writes the pushed position
to `+0x38`/`+0x40`, the hit normal to `+0x154`, the hit point to `+0x160` and bit 0 of `+0x16C`. The per-tick caller
`0x5A9D20` runs `0x631CA0` for the 8 character records and the NPC list `gp-0x5E6C` (it calls `0x5A9AC0` and `0x54BF70`,
994 lines, not read), then `0x606030` for the enemy list `gp-0x5E7C` (`0x5A9AC0` unless `+0x54A` bit 0x20, which adds
the velocity `+0xB28` directly, then the floor).

**Probes the action code uses (verified (code) for the first two; the rest not decoded).**
- `0x62DAE0`, the wall probe of the earlier note (call sites `0x596850`, `0x5990B0`, `0x61D1F0`, `0x646150`; not in the
  scratch, so not re-read).
- `0x62B880`: a ray from the position back along the last displacement (x100) to the position; on a solid hit it
  copies the hit into `+0xD00` and resets the previous position `+0x44`.
- `0x62ABA0`: four rays from the position along four directions (constants at `0x6DE730`), nearest wall within 10000,
  returning the heading difference to it.
- `0x629C30`, `0x629F70`, `0x62A8A0`, `0x62B180`, `0x62B380`, `0x62B4F0`: more probes from the action code (assumed:
  wall lean, climb, door approach).

**The head-in-wall fix, now concrete.**
